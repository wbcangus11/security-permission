# 设计导读 —— 怎么一步步看懂这套权限系统

> 写给第一次接手这套代码的人。目标:用最短路径建立"心智模型 → 引擎 → 难点"的理解,
> 而且**边读边能在浏览器里验证**,不靠死记。
>
> 配套文档:`权限设计说明.md`(通俗设计)、`海康对照.md`(为什么这么设计)、`测试报告.md`(行为字典)、`CLAUDE.md`(决策速查)。
>
> 行号会随迭代漂移,**锚点以函数名为准**(行号只是参考,找不到就按函数名搜)。

---

## 0. 先记住这一句话(心智模型)

> **每次访问 = 功能关(角色有没有这个菜单)+ 数据关(角色的树范围盖不盖到这个节点),两关都过才放行;超级管理员直接放行。**
> 写权限(建/改角色)时再叠一层**受控委派**:你能授出去的权限 ⊆ 你自己拥有的权限。

整套代码都在为这一句话服务。带着它去读,每个函数都能对号入座。

两个权限维度、两个前端域,一一对应:

| 维度 | 是什么 | 引擎入口 | 前端体现 |
|---|---|---|---|
| 功能权限 | 角色 → 菜单(分 SYS 系统域 / APP 应用域) | `CheckMenu` | 看得到哪些菜单/卡片 |
| 数据权限 | 角色 → 区域树 / 组织树 / 业务资源 | `CheckArea` / `CheckOrg` / `CheckResource` | 看得到哪些区域、哪些摄像头、能点哪些操作 |

## 2. 学词汇:领域模型(`internal/model/permission.go`,全文约 100 行)

这是整套设计的"名词表",**必须先吃透**,后面所有代码都在操作这几个结构:

- `Area` / `Org` —— 树;关键字段是 `Path`(形如 `/1/3/4/`,**物化路径**)。**为什么要存 Path?** 带着这个问题往下读。
- `Role` —— 一个角色聚合**全部**权限:
  - `MenuCodes` / `MenuIds`(功能;接口和前端优先用稳定 `code`,数据库关系仍保存 `menu_id`)
  - `AreaScopes` / `OrgScopes` / `ResourceAreaScopes`(数据,都是 `DataScope`)
  - `CreatedBy`(创建人,委派用)
- `DataScope{NodeId, IncludeChild}` —— **整个数据权限就靠这个小结构**:授权"某节点 + 要不要含子树"。
- `User` —— `RoleIds`(绑多个角色)+ `IsSuperuser`(超管特例)。

**该问自己:** 数据权限为什么不存"展开后的所有子节点 id",只存"一个节点 + 是否含子树"?(答案在第 3 步。)

---

## 3. 读引擎(核心!`internal/logic/permission/auth.go`)

引擎是**只读的纯逻辑**,自成一体,最好懂。按顺序读:

| 顺序 | 看什么(函数) | aha |
|---|---|---|
| ① | `Decision` 结构 | 引擎不只回 true/false,还回 `Reason` + `Trace`(推理过程)——**这是你最好的老师**(见第 4 步) |
| ② | `isSuper` / `superDecision` | 超管在每一关开头**直接短路放行**,与数据模型解耦 |
| ③ | `CheckMenu`(功能关) | 最简单:根据菜单 code 找 `menu` 表记录,用户最终有效权限里有这个 code 就过 |
| ④ | **`checkTreeScope`(数据关·树)** | **全套设计的"题眼"**:`CheckArea` / `CheckOrg` 都只是调它(各传一个 `pick` 闭包选 `AreaScopes` 还是 `OrgScopes`)。看它怎么用 `strings.HasPrefix(targetPath, scPath)` 判断"目标在不在授权子树里" |
| ⑤ | `nodePath` | 回答第 2 步的问题:存 `Path` 就是为了把"含子树"判断变成**一次字符串前缀比较**;新增子节点天然落进前缀 → **自动继承**,不用重新授权 |
| ⑥ | `CheckResource`(应用域资源) | 资源所在区域落在 `ResourceAreaScopes` 内即通过;当前不做单资源操作覆盖 |

读完 ④⑤,你就抓住了这套设计**最聪明的一招**:树权限不展开、靠物化路径前缀判断子树,所以"授权一次,未来新增子节点自动继承"。

练习:
1. 测「**李四** 看 **1号楼大厅球机** 的 **远程回放**」→ ✅ 允许 + 原因。
2. 把那行原因(`Trace`)拿去对 `CheckResource` 的代码,**一行原因对一段代码**。
3. 再测它的 **实时预览** → ✅ 允许,看原因怎么变。

> 这一步做完,引擎对你就**不再是黑盒**——它会自己讲为什么。比读十遍代码都管用。

## 5. 啃难点:受控委派(`internal/logic/permission/delegation.go` + `role.go`)

全套**唯一烧脑**的地方(写时逻辑),前面都懂了再来。

1. `GrantableSet` —— "操作人自己能授出去的上限"(菜单返回 `menuCodes`,树/资源返回 ID,角色返回普通用户自建角色)。
2. `MergeDelegated` + `mergeScopes` —— 核心公式:
   ```
   保存后 = (本次提交 ∩ 操作人可授范围) ∪ (角色原有 \ 操作人可授范围)
            范围内,以提交为准              范围外,原样保留(看不到也删不掉)
   ```
   先看菜单那段,再看它对菜单/区域/组织/资源区域范围重复同一套路。
3. `ManageableRoles` + `GuardManageRole`(在 `role.go`)—— 当前规则:普通用户只能看见、分配、编辑、删除自己创建的角色;超管不受限。

**该问自己:** 为什么"范围外的原有权限要保留"而不是删掉?
→ 防止低权限操作人在编辑时**误删他根本看不见的高权限**(既防越权,又防误删)。

## 6. 看"水管":接口、实现、存储与缓存(`internal/service/permission.go` + `internal/logic/permission`)

懂了逻辑,再看数据怎么进出:

- `internal/service/permission.go` —— 只定义业务接口和 Provider 注册；控制器只依赖这一层。
- `internal/logic/permission/app.go` —— 组装共享 Store、鉴权、角色、用户、区域等具体实现，并注册到 service。
- `store.go` —— MySQL 数据的运行时不可变快照(map),菜单从数据库读,前后端用 `code` 交互。它只负责读模型和缓存,不是业务入口。
- `permission_cache.go` —— 只缓存紧凑菜单权限；区域/组织仍保留 scope + path 前缀语义，不为每个用户展开整棵树。
- `db.go` 的 `Store.Reload`(启动 / 每次写后载入)和 `Store.SaveRole`(底层落库)。角色保存的业务入口看 `RoleService.SaveBasic`,它会先做角色管理功能门禁、菜单 code 转换、created_by 保持、委派合并,再调用底层落库。
- **边界**:`Store` 方法集中在 `store.go`/`db.go`;`auth.go`/`delegation.go` 是 `PermissionService`;`area.go`/`org.go`/`resource.go`/`role.go`/`user.go` 是各自业务服务;`runtime.go`/`paging.go` 是 `ViewService`。看到 `func (s *Store)` 出现在业务文件里就说明边界又开始变乱了。
- `manifest/sql/menu.sql` + `tools/dbinit/main.go` —— 菜单/权限点按 `code` 幂等同步;旧库会补 `menu` 新列和唯一索引。
- **设计亮点**:`role_data_scope` **一张表**用 `scope_type`(AREA / ORG / RES_AREA)装下三类树范围。看 `Reload` 里的 `switch x.ScopeType` 和 `SaveRole` 里的 `insScope`——**加一种新范围只要加一个 case**。历史 `ROLE` 类型已停用,仅在删除角色时做兼容清理。

## 7. 收口:体验层 + 前端(`runtime.go` / `controller/perm/perm.go` / `resource/public/index.html`)

- `runtime.go` —— 不是鉴权,是"把鉴权结果包装成界面要的形状":`VisibleAreas`、`AreaResources`、`ManageAreas`…
- `paging.go` —— **数据权限的另一种"用"法**:`auth.go` 是"已知节点能不能看"(点查、读缓存、微秒级);`paging.go` 是"未知列表哪一页能看"(把 scope **拼成 SQL WHERE 下推数据库**,走 `area.path` 的 `idx_path`,支撑成千上万节点)。`treeScopeFilter`→`areaScopeWhere` 把"含子树授权"翻译成 `path LIKE '根path%'`(**一条 LIKE 顶一棵子树**)——这正是第 3 步物化路径红利在"列表/分页"场景的复用。**该问自己:** 为什么列表过滤不能像鉴权那样逐行调引擎?(答:列表是未知全集,逐行调=先全表捞回内存,大数据量直接退化;必须让数据库带着权限分页。)
- `perm_v1_routes.go` —— HTTP 接口,薄薄一层:收参数 → 调 service → 回 JSON。角色权限统一走 `/api/role/save`。
- `index.html` —— 纯 JS 无框架;角色配置的菜单树和区域树勾选 / 置灰,对应前面的 `GrantableSet`(超范围节点前端隐藏)。区域/资源区域树是惰性分层加载,保存时推断 `includeChild`。

写操作(如建区域 / 改资源)在哪把"两关"合起来?看 `area.go` / `resource.go`:**先过功能关(菜单)再过数据关(`CheckArea`)**,这就是"两维度同时满足"的落地点。

## 三个动手练习(验证你真的懂了)

1. **改一刀看现象**:去掉张三某角色的某区域权限 → 应用端切到张三,看那片区域消失 → 用鉴权测试看 `Trace` 怎么变。
2. **顺藤摸瓜(写链路)**:前端「保存角色」提交 `menuCodes` → `perm_v1_routes.go` `RoleSave` → `RoleService.SaveBasic` → `MenuIdsByCodes` → `MergeDelegated` → `Store.SaveRole` → `reloadRoles`,完整走一遍。
3. **复现一条测试**:从 `测试报告.md` 挑一条(如资源范围自动继承),在界面上摆出来,验证结果一致。
