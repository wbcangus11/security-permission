# 基于角色的权限设计说明(仿海康安防平台)

> 一句话:**不直接给用户配权限,而是把权限装进「角色」;角色里同时管两件事 —— 能用哪些功能(功能权限) + 能管哪些数据(数据权限)。**

---

## 1. 为什么这么设计

普通后台权限只要管"能不能进这个页面"就够了。但安防/监控这类系统,光这个不够,还要管:

- 这个人**能看哪几个区域**的摄像头?
- 能看的摄像头里,**哪些只能看实时、不能回放**?
- 一个区域管理员,**能不能再把权限分给别人**,分的时候会不会越权?

所以这套设计把权限拆成两个维度,交叉使用:

|              | 功能权限(能用什么功能)   | 数据权限(能管/看哪些对象)        |
| ------------ | -------------------------- | --------------------------------- |
| **系统管理域** | 系统管理菜单(配人、配设备…) | 安保区域树、组织树                |
| **应用域**     | 应用菜单(看监控、检索…)   | 业务资源(摄像头)+ 操作项(预览/回放) |

**两个维度必须同时满足才放行。** 比如"看回放":既要有"远程回放"这个功能菜单,又要这个摄像头在你的数据范围内。

---

## 2. 几个核心概念

| 概念         | 是什么                                   | 例子                          |
| ------------ | ---------------------------------------- | ----------------------------- |
| **角色**     | 权限的集合,分配给用户                   | 安防管理员、园区A值班员        |
| **用户**     | 登录账号,绑定一个或多个角色             | 张三、李四                     |
| **菜单**     | 功能项,树形,分系统管理域/应用域两类     | 角色管理、实时预览             |
| **区域树**   | 物理空间,树形,摄像头挂在它下面          | 根区域 > 园区A > 1号楼         |
| **组织树**   | 人/车的归属,树形                        | 根组织 > 技术部 > 安防组       |
| **资源**     | 业务对象,挂在某个区域下                  | 1号楼-大厅球机                 |
| **操作项**   | 资源上的动作                             | 实时预览、远程回放、图片查询   |

## 3. 数据权限怎么"挂"在树上(关键)

### 3.1 勾选 = 授权一棵子树

给角色配区域权限时,**勾选某个节点 = 授权这个节点及它下面的整棵子树**。

```
☑ 园区A          ← 勾这一个
   1号楼         ← 自动包含
   2号楼         ← 自动包含
   (以后新增的3号楼)← 自动包含!
```

### 3.2 不展开存储,用"路径前缀"判断

每个树节点存一个**物化路径** `path`,形如 `/1/3/4/`(含自己),代表它在树里的位置。

判断"目标节点是否在某个授权子树内",只要看路径前缀:

```
授权了 园区A (path=/1/3/)
判断 1号楼 (path=/1/3/4/) 在不在范围内?
  /1/3/4/  以  /1/3/  开头  →  在!
```

**好处:** 数据库里只存"勾了哪个节点 + 是否含子树",不用把几千个子节点全列出来;以后区域树新增节点,**自动继承父节点权限**,不用重新配。这就是海康那句"新增资源继承所在区域"。

### 3.3 业务资源:范围 + 精细两层

应用域看视频的权限,分两层配:

1. **粗粒度(范围)**:按区域勾定"能看哪片区域的摄像头",新增摄像头自动纳入。
2. **细粒度(精细)**:对单个摄像头单独配操作项。

判断规则:

```
某摄像头 + 某操作(如 102号球机 + 远程回放)能不能用?
├─ 摄像头所在区域不在你的资源范围内 → 拒绝
├─ 这个摄像头配了"精细" → 只给精细里勾的操作(覆盖模式;一个不勾=零操作)
└─ 没配精细 → 范围内默认给全部操作(继承模式)
```

例:李四的范围是"园区A",但对 102号球机单独配了"只给实时预览" → 他能看 102 的实时预览,但**不能回放**;而同区域没单独配的 104,他**所有操作都能用**。

#### 3.3.1 资源级可见(对齐海康前台两级)

可见性也是两级,与上面的"范围/精细"对应:

- **区域级(L1)**:区域在资源范围内 → 该区域下资源默认都可见(继承)。
- **资源级(L2)**:**「精细模式 + 一个操作都不勾」= 该资源零权限 → 应用端从资源列表隐藏(资源级不可见)**;只要有任一操作,就可见。

这对齐海康前台「区域级勾选(继承)+ 高级配置逐资源『查看』(覆盖,没勾即不可见)」。
实现上,"精细模式"被**显式持久化**(`Role.ResourceOverrides`,复用 `role_data_scope` 的 `scope_type='RESOVR'`),
否则"精细+0操作"会塌缩成"继承全开"而无法表达隐藏;运行时 `AreaResources` 过滤掉零操作资源。
判定 `hasOverride = ResourceOverrides ∪ 有操作行`,兼容旧数据(老角色靠操作行隐含精细,行为不变)。

### 3.4 大数据量:把权限"下推"给数据库分页

前面讲的都是**点查**:已知一个节点,问"在不在范围内"(读内存缓存,微秒级)。
但前端还要列**树**和**资源列表**——这是另一类问题:节点是未知全集,问"**这一页里哪些我能看**"。
区域成千上万时,"全捞回内存再逐行过滤"会退化成全表扫,扛不住。

办法:把"路径前缀"那招(§3.2)从内存判断**翻译成 SQL 条件下推数据库**,让数据库带着权限分页:

```
你的范围 = { 园区A 含子树 }
区域树某一层 / 资源列表,加一句 WHERE：
   area.path LIKE '/1/3/%'        ← 一条 LIKE 顶整棵子树,还走 path 索引
仅勾本节点(不含子树) → WHERE id = 该节点
勾了根/超管          → 不加任何条件(看全部)
什么都没勾            → 直接返回空(连库都不查)
```

配合两个体验优化:

- **树按层懒加载**:点开一个节点才查它的直接子区域(`parent_id=该节点`),不是一次性拉整棵树。
- **导航祖先**:你对深层节点有权、但中间层无权时,中间层仍要显示(否则点不进去)。它们标为"仅可见"(灰色),只能展开、不能操作。

这样同一套范围,既能回答"能不能看某个节点"(鉴权),也能回答"这一页能看哪些"(列表分页),且都建立在 §3.2 那一个 `path` 字段上。零新增表结构。

## 4. 鉴权流程(运行时三关)

一次请求要连过三关,任一不过就拒绝:

```
1. 功能关:请求的菜单/接口,在用户角色的菜单列表里吗?
2. 数据关:要操作的对象(摄像头/人员),它所在的区域/组织,
          落在用户角色的数据范围(授权子树)里吗?
3. 操作关:这个对象 + 这个动作(预览/回放),被授权了吗?
```

性能上:用户登录后,把"菜单集合 + 区域路径前缀集合"算好缓存起来,请求时只做集合/前缀匹配,不用每次查库。

## 5. 二次授权(受控委派)—— 重点

### 5.1 是什么

如果给一个角色配了"角色管理 / 账号管理"菜单,拥有这个角色的用户就能**创建子角色、分配权限给别人**。但有个铁律:

> **他能授出去的权限,必须 ⊆ 他自己拥有的权限。权限只能收窄,不能放大。**

比如李四只有"园区A + 实时预览",那他建子角色时:

- 区域只能从园区A子树里选,选不到园区B;
- 菜单只能从他有的里面选,看不到"角色管理"。

### 5.2 这套用的是哪种语义(写时保留 + 运行时收窄)

经过在真实海康平台测试,海康原始行为更接近 **模型 A:写时校验 + 合并保留,不级联**。本项目按当前业务要求采用更严格的语义:**写时仍保留编辑者看不见的旧授权,运行时再与创建人的当前有效权限取交集**。具体三条:

1. **已建角色运行时收窄**:如果创建人后来被收权了,他**之前建好的角色存量授权不直接删除**,但关联该角色的用户实际鉴权时不能再使用创建人已失去的范围。
2. **编辑界面实时过滤**:创建人再打开角色编辑页时,**只看得到他当前还能授的那部分**,超范围的看不见。
3. **看不见的不会被删**:保存时,他范围外、角色原有的权限**原样保留**。

也就是合并公式:

```
保存后的角色权限
  = (本次提交 ∩ 创建人当前可授范围)   ← 范围内,以提交为准(可增可删)
  ∪ (角色原有权限 \ 创建人可授范围)   ← 范围外,原样保留(看不到也删不掉)
```

这样既**防越权**(超范围的提交被丢弃),又**防误删**(看不见的权限被保留)。

实际鉴权时还会追加一道动态上限:

```
角色实际生效权限 = 角色存储权限 ∩ 创建人当前有效权限
```

落点:`service/auth.go` 在 `CheckMenu` / `CheckArea` / `CheckOrg` / `CheckResource` 判定命中角色后,再检查该角色 `created_by` 对应创建人当前是否仍拥有目标权限;`created_by=0` 或创建人为超级管理员时不收窄。这样管理员收回张三的区域后,张三以前创建的角色即使数据库里仍保留旧区域,李四运行时也不能继续访问该区域。

### 5.3 谁能看见 / 谁能管(编辑·删除)哪些角色 —— 当前简化规则

5.2 解决的是「**能授出哪些权限**」;这一节解决「**能看见 / 能管理哪些角色**」。按 **2026-06-17 用户要求**,当前系统不再提供额外的「角色范围」配置,普通用户只围绕自己创建的角色工作:

```
可见/可分配 manageable(操作人) = (操作人自己创建的角色)      ← 靠 created_by
可编辑/删除 owned(操作人)      = (操作人自己创建的角色)          ← 仅自建
```

即普通用户只能看见、分配、编辑、删除自己创建的角色;超级管理员/不受限操作人可见并管理全部角色。

- **操作人(actor)= 当前登录用户**:角色管理页**不再有**独立「操作者(创建人)」下拉(旧下拉默认「不受限」会让任何登录用户越权——曾导致「王五能删 admin 创建的角色」,已移除);可见/编辑/删除一律按登录身份判定,切「当前登录」即换操作者。
- **自建角色**由 `role.created_by` 判定。`created_by` 只在新建角色时写入,编辑时保持原值不变。
- **可见/可分配集 manageable** 驱动:角色列表显示、账号绑定角色的可选范围。普通用户仅自建;超级管理员/不受限操作人全部可见。
- **可编辑/删除集 owned** 驱动:角色列表的 canEdit/canDelete(非自建角色前端置 🔒 只读、删除按钮隐藏,后端 `GuardManageRole`→`OwnedRoles` 兜底拒绝)。
- 落点:`service/delegation.go`(`ManageableRoles`/`OwnedRoles`)、`service/role.go`(`GuardManageRole`→`OwnedRoles`)、`index.html`(`roleCanSee`/`roleCanManage`,`actorId()=loginUserId()`)。
- 历史说明:旧版本曾复用 `role_data_scope.scope_type='ROLE'` 做显式角色范围;当前版本不再读取/保存该类型,仅删除角色时兼容清理遗留引用。

## 6. 数据库表

建表见 `manifest/sql/schema.sql`(幂等),种子数据见 `manifest/sql/seed.sql`。核心 11 张表:

| 表                       | 作用                                              |
| ------------------------ | ------------------------------------------------- |
| `area` / `org`           | 区域树 / 组织树(含物化路径 `path`)               |
| `menu`                   | 菜单树,`domain` 区分 SYS/APP                      |
| `resource`               | 业务资源(挂区域下)                              |
| `action`                 | 操作项                                            |
| `role`                   | 角色,`created_by` 记录创建人(委派用)            |
| `role_menu`              | 角色-菜单(功能权限)                              |
| `role_data_scope`        | **角色-数据范围**,`scope_type`=AREA/ORG/RES_AREA/**RESOVR** + `include_child` |
| `role_resource_action`   | 角色-资源操作(精细授权,逐操作)                  |
| `user` / `user_role`     | 用户 + 角色绑定                                   |

设计要点:三棵树的范围授权**合并进一张 `role_data_scope`**,用 `scope_type` 区分,少维护、好扩展;复用同一张表的还有资源「精细模式」标记(资源级可见,见 3.3.1,`scope_type='RESOVR'`、`node_id`=精细资源 id,`include_child` 不参与判定)。

核心鉴权 SQL(子树判断):

```sql
-- 判断用户能否管理某区域
SELECT EXISTS(
  SELECT 1 FROM user_role ur
  JOIN role_data_scope s ON s.role_id=ur.role_id AND s.scope_type='AREA'
  JOIN area target  ON target.id = ?areaId
  JOIN area granted ON granted.id = s.node_id
  WHERE ur.user_id = ?uid
    AND (s.node_id = ?areaId
         OR (s.include_child=1 AND target.path LIKE CONCAT(granted.path,'%')))
);
```

## 7. 代码结构

```
internal/
  model/permission.go        领域模型(Area/Org/Menu/Resource/Role/User…)
  service/
    store.go                 内存缓存 + 读方法
    db.go                    从 MySQL 加载(Reload)/ 写回(SaveRole)
    auth.go                  鉴权引擎(三关判断)★
    delegation.go            二次授权:可授范围(GrantableSet)+ 合并(MergeDelegated)★
  controller/perm/perm.go    HTTP 接口
  cmd/cmd.go                 路由 + 启动时加载数据
resource/public/index.html   前端测试页(仿海康角色编辑 UI + 鉴权测试)
manifest/sql/schema.sql      建表 DDL(幂等,CREATE IF NOT EXISTS)
manifest/sql/seed.sql        种子(演示)数据
tools/dbinit/main.go         幂等初始化:建表 + 空库才灌种子,保留已有数据
```

**数据流**:MySQL 是持久层;启动时 `Reload` 全量载入内存缓存;鉴权读缓存(快);写角色时落库再刷新缓存。

## 9. HTTP 接口

| 方法 | 路径                      | 说明                                  |
| ---- | ------------------------- | ------------------------------------- |
| GET  | `/api/meta`               | 区域/组织/菜单/资源/操作/用户 全部元数据 |
| GET  | `/api/role/list`          | 角色列表                              |
| GET  | `/api/role/detail?id=<id>` | 角色详情                             |
| POST | `/api/role/save?actor=<uid>` | 保存角色(actor=创建人,0=不受限)走委派合并 |
| POST | `/api/role/delete?actor=<uid>` | 删除角色(body 含 id)             |
| GET  | `/api/role/grantable?actor=<uid>` | 操作者可授出的范围上限(前端隐藏用) |
| POST | `/api/auth/check`         | 鉴权测试,返回 allow + 判定轨迹       |
| GET  | `/api/app/area-children`  | 应用端区域树按层懒加载               |
| GET  | `/api/manage/area-children` | 后台区域树按层懒加载               |
| POST | `/api/manage/area-save`   | 新增/重命名/移动区域                 |
| POST | `/api/manage/org-save`    | 新增/重命名/移动组织                 |
| POST | `/api/manage/resource-save` | 新增/重命名/移动资源               |

`/api/auth/check` 请求体:

```jsonc
{ "userId":2, "type":"menu",     "code":"sys.person.role" }   // 功能
{ "userId":2, "type":"area",     "nodeId":3 }                 // 区域数据
{ "userId":2, "type":"resource", "resourceId":102, "action":"playback" } // 资源+操作
```
