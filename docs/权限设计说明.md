# 权限系统设计说明

当前项目只有一套运行环境，按单体单实例设计，不保留演示模式、旧接口或兼容分支。

## 1. 权限模型

用户不直接保存权限，而是绑定一个或多个角色：

```text
用户 -> 角色 -> 菜单权限
             -> 后台区域范围 AREA
             -> 组织范围 ORG
             -> 视频监控区域范围 RES_AREA
```

- `SYS` 菜单控制后台管理功能。
- `APP` 菜单控制前台应用功能。
- `AREA` 只控制后台区域管理。
- `ORG` 控制组织及账号管理范围。
- `RES_AREA` 控制视频监控资源范围；当前所有前台区域权限都使用它。
- 超级管理员直接拥有全部功能和数据权限。

摄像头操作固定为实时预览、远程回放、图片查询，直接映射到对应 APP 菜单，不需要单独的 `action` 表。

## 2. 树形数据权限

区域和组织都保存物化路径，例如 `/1/3/4/`。角色范围只保存：

```json
{ "nodeId": 3, "includeChild": true }
```

- `includeChild=false`：只授权节点本身。
- `includeChild=true`：授权节点及整棵子树，未来新增子节点自动继承。
- 点鉴权通过比较路径前缀完成。
- 树和资源列表把权限范围转换成 SQL `WHERE`，由数据库过滤和分页，不把整张表加载到服务内存。

一次业务访问同时检查功能菜单和数据范围。例如播放摄像头录像必须同时满足：

1. 用户角色包含远程回放菜单；
2. 摄像头所在区域落在用户的 `RES_AREA` 范围内。

## 3. 角色创建与二次授权

角色采用“写时限制、保存后独立生效”：

- 创建或编辑角色时，普通管理员只能授予自己当前拥有的权限。
- 超出管理员当前范围的提交不会生效。
- 管理员当前看不到的角色旧权限会原样保留，避免编辑时误删。
- 角色保存后只按自身存储的权限生效，不再依赖创建人的当前权限。
- 创建人被收权或删除，不会自动改变已保存角色及其绑定用户的权限。

例如 A 创建 R1 给 B，B 创建 R2 给 C。A 收紧 R1 后，B 的权限和可授权范围随 R1 变化，但 R2 和 C 的权限不变。

`role.created_by` 只用于角色归属和审计：普通管理员只能查看、编辑、删除自己创建的角色，超级管理员可以管理全部角色。

## 4. 缓存与一致性

MySQL 是唯一事实来源。服务只保留两级临时复用：

1. 请求级判定器：保存一次操作实际读取的数据，请求结束即释放。
2. 进程级热缓存：按需缓存访问过的用户、角色、区域、组织、资源和菜单。

热缓存具有 TTL 和条目上限，不会启动全表预加载。相同 key 的并发冷加载会合并，避免缓存失效时击穿数据库。

角色、用户绑定、区域、组织或资源写事务提交后会同步清空热缓存并递增版本。版本检查可以阻止写事务之前已经开始的慢查询把旧数据重新放回缓存。

当前是单实例，因此不需要 Redis、消息总线或分布式失效协议。权限表只能通过本服务修改；如果直接修改数据库，需要同步重启服务。

## 5. 数据库

当前共 9 张业务表：

| 表 | 作用 |
| --- | --- |
| `user` | 用户 |
| `role` | 角色及创建人 |
| `user_role` | 用户与角色绑定 |
| `menu` | 菜单和稳定权限码 |
| `role_menu` | 角色菜单权限 |
| `role_data_scope` | AREA、ORG、RES_AREA 三类树范围 |
| `area` | 区域树 |
| `org` | 组织树 |
| `resource` | 摄像头等业务资源 |

数据库基线在 `manifest/sql/schema.sql`，菜单在 `manifest/sql/menu.sql`，初始化数据在 `manifest/sql/seed.sql`。

## 6. 代码结构

```text
api/perm/v1/                  HTTP 请求定义
internal/controller/perm/     收参和统一响应
internal/logic/permission/    权限判断、写业务、查询和热缓存
internal/middleware/identity.go
                               X-User-Id 身份边界
internal/model/               领域模型及数据库模型
internal/dao/                 GoFrame DAO
resource/public/index.html    当前管理页面
tools/dbinit/main.go          数据库重建工具
```

单体内部直接调用 `logic/permission` 的包函数，不维护 service 接口、Provider 注册器或全局 Application 对象。

## 7. HTTP 接口

- `/api/meta`：角色和用户管理页面初始化字典。
- `/api/app/menu`、`/api/manage/menu`：当前用户可见菜单。
- `/api/app/area-*`：固定使用 `RES_AREA`。
- `/api/app/resource-list`：按 APP 菜单和 `RES_AREA` 返回资源。
- `/api/manage/area-*`：固定使用 `AREA`。
- `/api/manage/org-*`：固定使用 `ORG`。
- `/api/manage/resource-*`：资源管理。
- `/api/role/*`：角色、可授权范围和角色配置树。
- `/api/user/*`：用户及角色绑定管理。

当前操作者统一从 `X-User-Id` 请求头读取，写接口不接受额外的操作者 ID。
所有接口只返回一层 `{code, message, data}`，不保留旧的双层响应兼容结构。

## 8. 运行与验证

```powershell
# 需要重建当前数据库时
go run ./tools/dbinit --recreate

# 启动
go run .

# 验证
go test ./...
go vet ./...
go build ./...
```

默认页面地址为 `http://127.0.0.1:8001/`，数据库和服务配置统一位于 `manifest/config/config.yaml`。
