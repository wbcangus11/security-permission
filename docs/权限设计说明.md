# 权限系统设计说明

当前项目只有一套运行环境，按单体单实例设计，不保留演示模式、旧接口或兼容分支。

## 1. 权限模型

用户不直接保存权限，而是绑定一个或多个角色：

```text
用户 -> 角色 -> 菜单权限
             -> 后台区域范围 AREA
             -> 组织范围 ORG
             -> 视频监控区域范围 RES_AREA
```

- `SYS` 菜单控制后台管理功能。
- `APP` 菜单控制前台应用功能。
- `AREA` 只控制后台区域管理。
- `ORG` 控制组织及账号管理范围。
- `RES_AREA` 控制视频监控资源范围；当前所有前台区域权限都使用它。
- 超级管理员直接拥有全部功能和数据权限。

摄像头操作固定为实时预览、远程回放、图片查询，直接映射到对应 APP 菜单，不需要单独的 `action` 表。

## 2. 树形数据权限

区域和组织都保存物化路径，例如 `/1/3/4/`。角色范围只保存：

```json
{ "nodeId": 3, "includeChild": true }
```

- `includeChild=false`：只授权节点本身。
- `includeChild=true`：授权节点及整棵子树，未来新增子节点自动继承。
- 点鉴权通过比较路径前缀完成。
- 树和资源列表把权限范围转换成 SQL `WHERE`，由数据库过滤和分页，不把整张表加载到服务内存。

一次业务访问同时检查功能菜单和数据范围。例如播放摄像头录像必须同时满足：

1. 用户角色包含远程回放菜单；
2. 摄像头所在区域落在用户的 `RES_AREA` 范围内。

## 3. 角色创建与二次授权

角色采用“写时限制、保存后独立生效”：

- 创建或编辑角色时，普通管理员只能授予自己当前拥有的权限。
- 角色列表只返回角色基本信息；角色详情按当前登录的编辑人投影，只返回其当前可授予的权限。
- 新增菜单或树范围超出管理员当前可授权范围时，整次权限事务失败，不会静默忽略。
- 授予 `includeChild=true` 时，管理员必须拥有该节点或其祖先的子树权限；只有单节点权限不能向下扩成子树。
- 角色基本信息和权限分别保存；只修改名称或描述绝不会改动权限。
- 系统配置菜单和应用菜单分别提交当前编辑人可见部分的完整 code 快照；AREA、ORG、RES_AREA 三类树范围提交明确的 `adds` / `dels`。
- 没有出现在树权限 `adds` / `dels` 中的旧记录保持不变，后端不再根据整棵树快照猜测用户意图。
- 超出编辑人当前可授权范围的历史权限不会展示，保存时由后端原样保留；增删请求都不能越过这一范围。
- 角色保存后只按自身存储的权限生效，不再依赖创建人的当前权限。
- 创建人被收权或删除，不会自动改变已保存角色及其绑定用户的权限。

例如 A 创建 R1 给 B，B 创建 R2 给 C。A 收紧 R1 后，B 的权限和可授权范围随 R1 变化，但 R2 和 C 的权限不变。

`role.created_by` 只用于角色归属和审计：普通管理员只能查看、编辑、删除自己创建的角色，超级管理员可以管理全部角色。

角色只有一个写接口 `/api/role/save`。基本信息始终随请求提交，权限部分按脏状态选择性提交：

- 省略 `permissions`：只保存名称和描述，所有权限保持不变。
- `permissions.menuConfig` 和 `permissions.menuApp` 分别控制系统配置菜单和应用菜单；省略其中一项表示该域保持不变，传 `{"replace":[]}` 表示清空当前编辑人可管理的部分，范围外旧权限仍保持不变。
- AREA、ORG、RES_AREA 只应用各自 `adds` / `dels`，没有出现的记录保持不变。
- 新建或更新角色时，基本信息和本次权限变化在一个数据库事务中提交，任一步失败都会整体回滚。

## 4. 权限快照缓存与一致性

MySQL 是唯一持久化事实来源。服务保留两类只读内存数据：

1. 用户权限快照缓存：按用户保存账号、有效角色、菜单 code 和三类树范围，默认 5 分钟过期。
2. 进程级菜单目录：启动时一次性加载全部菜单，按 code 建立只读索引，进程运行期间无 TTL、无淘汰。

菜单是随版本发布的稳定权限字典。代码中的 `builtInMenus` 是菜单基线，应用启动时幂等写入数据库后按 code 加载；`parent_code` 表示菜单父子关系，`role_menu.menu_code` 表示角色菜单关系。菜单加载或树结构校验失败时应用拒绝启动。

请求先按用户 ID 查询权限快照缓存。命中后鉴权阶段不访问数据库；未命中时固定批量查询用户、角色、角色菜单和带节点路径的数据范围，不再按角色或节点产生 N+1 查询。

用户或角色写事务提交后只失效受影响用户。角色删除会在级联删除前记住绑定用户，再精准清理这些用户的快照。区域、组织结构写入很少见，基础版本先统一清理权限快照；资源不属于快照内容，因此资源写入不用清缓存。

缓存失效带版本检查：如果一次旧查询尚未结束时权限刚好被修改，旧查询结果不会重新写回缓存，当前请求也会丢掉这份旧结果并重新加载。权限快照只做纯判断，不保存 HTTP 请求、不查询任意业务对象，也没有隐藏错误字段。

当前是单实例，因此使用进程内缓存，不需要 Redis、消息总线或分布式失效协议。直接绕过服务修改数据库时，用户快照最迟在 TTL 到期后更新；直接修改稳定菜单字典后需要重启服务重新加载菜单目录。

## 5. 数据库

当前共 9 张业务表：

| 表 | 作用 |
| --- | --- |
| `user` | 用户 |
| `role` | 角色及创建人 |
| `user_role` | 用户与角色绑定 |
| `menu` | 菜单和稳定权限码 |
| `role_menu` | 角色菜单权限 |
| `role_data_scope` | AREA、ORG、RES_AREA 三类树范围 |
| `area` | 区域树 |
| `org` | 组织树 |
| `resource` | 摄像头等业务资源 |

数据库基线在 `manifest/sql/schema.sql`，菜单在 `manifest/sql/menu.sql`，初始化数据在 `manifest/sql/seed.sql`。

## 6. 代码结构

```text
api/perm/v1/                  HTTP Req/Res DTO 定义
internal/controller/perm/     API DTO 与 service model 的双向映射
internal/logic/permission/    对外鉴权方法、用户权限快照缓存、写业务和显式查询
internal/middleware/identity.go
                               认证中间件与 ctx 身份访问边界
internal/model/               service 输入输出、领域模型及数据库模型
internal/dao/                 GoFrame DAO
resource/public/index.html    当前管理页面
tools/dbinit/main.go          数据库重建工具
```

单体内部直接调用 `logic/permission` 的包函数，不维护 service 接口、Provider 注册器或全局 Application 对象。

## 7. HTTP 接口

- `/api/meta`：角色和用户管理页面初始化字典。
- `/api/app/menu`、`/api/manage/menu`：当前用户可见菜单。
- `/api/app/area-*`：固定使用 `RES_AREA`。
- `/api/app/resource-list`：按 APP 菜单和 `RES_AREA` 返回资源。
- `/api/manage/area-*`：固定使用 `AREA`。
- `/api/manage/area-save`：只负责新增和重命名；已有区域的 `parent_id` 不可修改。
- `/api/manage/area-reorder`：接收两个区域 ID，校验属于同一父节点后直接交换 `sort`，不允许跨父级。
- `/api/manage/org-*`：固定使用 `ORG`。
- `/api/manage/resource-*`：资源管理。
- `/api/role/*`：角色、可授权范围和角色配置树。
- `/api/user/*`：用户及角色绑定管理。

实际项目由认证中间件解析用户信息并写入 `context.Context`，权限包统一通过 `middleware.GetUserId(ctx)` 获取当前操作者；Controller 和 Service 不解析 Token、Session 或身份请求头，也不接收额外的操作者 ID。当前仓库只是用演示中间件把 `X-User-Id` 写入相同的 ctx 身份位置，替换认证接入时不需要修改业务代码。
所有接口只返回一层 `{code, message, data}`，不保留旧的双层响应兼容结构。
列表型接口统一把结果放在 `data.items`；controller 的出入参只使用 `api/perm/v1`
中的 `XxxReq` / `XxxRes`，不会直接向 HTTP 暴露 `internal/model`。

## 8. 运行与验证

```powershell
# 需要重建当前数据库时
go run ./tools/dbinit --recreate

# 启动
go run .

# 验证
go test ./...
go vet ./...
go build ./...
```

默认页面地址为 `http://127.0.0.1:8001/`，数据库和服务配置统一位于 `manifest/config/config.yaml`。
