# 权限框架核心设计

> 本文是一份与语言、框架、数据库和现有项目代码无关的权限设计契约。
>
> 另一个 Agent 应先理解本文的业务语义，再结合实际项目结构、用户补充要求和现有技术规范完成实现，不能照搬本文中的概念名称作为代码结构。

## 1. 文档边界

本文只确定权限框架必须保持的业务规则，不规定：

- 使用什么编程语言、Web 框架或数据库；
- 采用什么目录、分层、函数名、接口路径和请求结构；
- 用户身份通过 Token、Session、单点登录还是网关认证；
- 树使用物化路径、闭包表还是其他存储方式；
- 使用本地缓存还是分布式缓存；
- 前端页面和交互如何实现。

实际实现时，用户针对真实项目给出的提示优先于本文中的可选实现建议；但默认拒绝、权限域隔离、不可越权授权、事务一致性等安全不变量不能被弱化。

## 2. 要解决的问题

本框架组合三类能力：

1. 身份：当前请求是谁发起的。
2. 功能权限：该用户能否执行某类业务操作。
3. 数据权限：该用户能对哪些业务对象执行该操作。

角色既是权限集合，也是普通管理员向下授权的载体。

一次业务访问的最终结果是：

```text
允许访问 = 身份有效
        AND 拥有目标功能权限
        AND 目标对象落在该业务固定的数据权限域内
```

任何条件不满足都必须拒绝。前端展示结果不能作为服务端放行依据。

## 3. 核心领域模型

### 3.1 主体与角色

- 用户是发起业务请求的主体。
- 用户可以绑定多个角色。
- 角色包含功能权限和数据范围。
- 普通用户的最终权限是所有角色权限的并集。
- 用户不直接保存零散权限，避免角色权限与用户直授权形成两套难以解释的来源。

逻辑关系如下：

```text
用户 --多对多--> 角色 --多对多--> 功能权限
                         |
                         +--一对多--> 数据范围授权
```

### 3.2 功能权限

功能权限使用稳定且不随展示名称变化的唯一标识。

功能菜单的父子关系只服务于导航和展示：

- 子功能可见时，可以补齐父级目录用于展示；
- 补齐父目录不代表用户真正拥有父目录对应的业务权限；
- 服务端必须检查目标操作对应的真实功能权限，不能检查“菜单是否显示”。

管理端功能与应用端功能应分域维护，避免后台管理能力和前台业务操作混在一起。

### 3.3 数据权限域

当前设计存在三个彼此独立的数据权限域：

| 权限域 | 控制对象 |
| --- | --- |
| `AREA` | 区域结构管理，以及后台对区域内资源的管理 |
| `ORG` | 组织结构、用户可见范围和用户管理范围 |
| `RES_AREA` | 应用端业务资源的可见与可操作范围 |

`AREA` 和 `RES_AREA` 可以引用同一棵区域树，但表达完全不同的授权目的：

- 能维护一个区域，不代表能在应用端查看该区域的业务资源；
- 能查看一个区域的业务资源，不代表能维护区域结构或资源档案；
- 组织权限不能参与区域或资源判断。

每项业务能力使用哪个权限域必须由服务端固定，客户端不能通过参数选择或切换权限域。

### 3.4 数据范围授权

一条树范围授权至少包含：

- 权限域；
- 节点；
- 是否包含后代。

语义固定为：

- 不包含后代：只覆盖节点本身；
- 包含后代：覆盖节点本身、当前全部后代以及未来新增后代。

同一用户来自多个角色的同类范围取并集，不取交集。

### 3.5 超级管理员

超级管理员是权限引擎的明确特例：

- 默认拥有当前和未来的全部功能权限；
- 默认覆盖三个数据权限域中的全部对象；
- 不依赖普通角色授权记录才能生效；
- 可以管理全部角色和用户。

普通管理员不能创建、修改或删除超级管理员，也不能把普通用户提升为超级管理员。系统必须始终保留至少一个可用的超级管理员。

## 4. 身份边界

真实项目中的认证中间件负责解析和校验用户身份，并把可信用户信息写入请求上下文。

权限逻辑和业务逻辑只从上下文读取当前用户，不重复解析 Token、Session、Cookie 或请求头，也不允许客户端在业务参数中提交操作者 ID。

必须满足：

- 上下文中没有有效身份时默认拒绝；
- 用户不存在、已失效或不可用时默认拒绝；
- 不能在身份缺失时回退读取普通请求参数；
- 上下文只承载可信身份，不把客户端携带的角色和权限声明当成实时授权事实；
- 当前有效角色和权限应从服务端可信数据源获取。

认证负责回答“你是谁”，权限框架负责回答“你能做什么、能操作哪些数据”，两者边界不能混淆。

## 5. 鉴权核心规则

### 5.1 默认拒绝

以下情况全部拒绝：

- 没有可信身份；
- 用户不存在或状态无效；
- 普通用户没有角色；
- 没有目标功能权限；
- 没有目标数据范围；
- 数据范围引用的节点不存在；
- 无法确定业务对象属于哪个权限节点；
- 无法确定业务操作应该使用哪个权限域。

### 5.2 功能权限与数据权限取交集

对象型业务不能只判断功能权限，也不能只判断数据权限。

例如，后台修改资源需要同时具备：

- 资源管理功能；
- 资源所属区域的 `AREA` 权限。

应用端查看同一资源需要同时具备：

- 对应应用功能；
- 资源所属区域的 `RES_AREA` 权限。

### 5.3 树范围判断

判断一个节点是否在授权范围内时：

- 任意一条子树授权覆盖目标节点即可通过；
- 任意一条单点授权与目标节点相同即可通过；
- 不存在命中范围时拒绝；
- 多角色、多范围之间均按“任一命中”合并。

树的具体存储方式可以变化，但必须可靠支持祖先、后代、单点和子树判断。

### 5.4 列表、搜索与统计

数据权限必须参与数据源查询，而不是先读取全量数据再在业务内存中过滤。

必须保证：

- 数据列表、搜索、总数和分页使用完全相同的权限条件；
- 没有任何范围时生成永不命中的条件，不能退化为不加条件的全量查询；
- 不通过逐对象鉴权产生大量重复查询；
- 越权对象不能出现在下拉选项、搜索建议、统计结果或导出数据中。

### 5.5 导航祖先

用户只拥有深层节点时，可以返回必要祖先帮助展示树路径，但必须区分：

- 可访问节点：可以查看详情并参与业务操作；
- 导航节点：只能用于展开到授权节点。

导航节点不能因为被展示而获得详情、写入或资源访问权限。

## 6. 功能与权限域映射

实现前必须为每项业务能力建立固定映射：

| 业务类型 | 功能权限 | 数据权限域 |
| --- | --- | --- |
| 区域结构管理 | 对应的区域管理功能 | `AREA` |
| 后台资源档案管理 | 对应的资源管理功能 | `AREA` |
| 组织结构管理 | 对应的组织管理功能 | `ORG` |
| 用户管理 | 对应的用户管理功能 | `ORG` |
| 角色管理 | 对应的角色管理功能 | 角色归属与操作者可授权上限 |
| 应用端资源操作 | 每种操作各自的应用功能 | `RES_AREA` |

应用端同一资源的不同操作可以对应不同功能权限。用户能看到资源，不代表自动拥有该资源的所有操作。

## 7. 角色管理与二次授权

### 7.1 角色归属

每个角色需要记录其归属或创建来源。

- 普通管理员只能查看和管理自己创建的角色；
- 超级管理员可以管理全部角色；
- 系统内置角色不归属于普通用户；
- 创建人被删除后，已有角色和角色绑定仍然生效，由超级管理员接管维护。

### 7.2 不可越权授权

普通管理员只能授予自己当前拥有的权限。

功能权限：操作者拥有某功能时，才能把该功能授予角色。

树范围：

- 操作者拥有节点单点时，只能授予该节点单点；
- 操作者拥有覆盖该节点的子树范围时，才可以授予该节点子树；
- 单点权限不能被放大为子树权限；
- 新增、删除或改变范围类型都必须检查操作者当前授权上限。

只要一次角色变更中存在任何越权内容，整个变更都应该失败，不能只保存合法部分。

### 7.3 不可见历史权限

角色可能包含操作者过去可以管理、现在已经无权管理的历史权限。

普通管理员编辑角色时：

- 详情只展示自己当前可管理的部分；
- 未展示的历史权限必须原样保留；
- 不能因为前端没有提交不可见部分，就把这些权限删除；
- 超级管理员可以看到并管理完整权限。

这是防止下级管理员误删上级或历史授权的关键规则。

### 7.4 权限变更语义

权限保存必须区分三种意图：

| 提交状态 | 业务语义 |
| --- | --- |
| 省略某类权限 | 该类权限保持不变 |
| 明确提交空集合 | 清空操作者当前有权管理的部分 |
| 明确提交增加或删除项 | 只应用这些变化 |

树权限推荐使用明确的增加和删除语义。把一个节点从单点改成子树，应视为删除旧授权并增加新授权，不能由后端根据模糊状态猜测。

角色基本信息和本次权限变化必须原子提交。任何一步失败都不能留下部分更新。

### 7.5 已保存角色独立生效

当前模型采用“授权时限制，保存后独立生效”：

- 创建或修改角色时，操作者不能超过自己的当前权限；
- 保存成功后，该角色按自身保存的权限独立生效；
- 创建人之后被收权或删除，不自动级联收回该角色及下游用户权限。

如果实际业务需要上游收权自动向下级联，必须额外设计持续委托关系，不能在现有模型中隐式实现。

## 8. 用户管理与角色绑定

### 8.1 用户可见和可管理范围

普通管理员管理用户时必须同时满足：

- 拥有用户管理功能；
- 目标用户所属组织位于操作者的 `ORG` 范围；
- 目标用户不是超级管理员。

创建用户或变更用户所属组织时，新组织也必须位于操作者的 `ORG` 范围。

### 8.2 可分配角色

- 超级管理员可以分配全部角色；
- 普通管理员只能主动分配自己创建的角色；
- 不存在的角色不能被绑定；
- 重复角色应按一条绑定处理。

编辑已有用户时，用户身上存在但当前管理员无权分配的历史角色必须保留。客户端新提交的越权角色不能进入最终结果。

### 8.3 用户安全保护

- 普通管理员不能创建或管理超级管理员；
- 用户不能删除自己当前正在使用的账号；
- 删除超级管理员前必须以并发安全的方式保证系统仍至少保留一个超级管理员；
- 用户主体与角色绑定变更必须原子提交。

## 9. 区域、组织与资源规则

### 9.1 区域

区域结构写入同时需要区域管理功能和相应 `AREA` 范围。

新增区域：

- 父区域必须存在；
- 操作者必须覆盖父区域；
- 同一父节点下名称不能重复；
- 新区域必须建立正确且可用于后代判断的层级关系。

更新区域：

- 只允许修改区域自身的普通属性，例如名称；
- 不允许改变父节点；
- 更新与排序必须是两个独立的业务命令；
- 不能通过更新命令隐式实现跨父级移动。

区域排序：

- 前端提交两个区域 ID；
- 两个区域必须存在；
- 两个区域必须属于同一父节点；
- 操作者必须同时覆盖两个区域；
- 不要求两个区域在当前顺序中相邻；
- 在同一事务中直接交换两个区域的排序值；
- 不重排或修改其他同级区域；
- 不修改任何区域的父节点和层级路径。

删除区域：

- 根区域受保护；
- 操作者必须覆盖目标区域；
- 只能删除没有子区域、没有业务资源的叶子区域；
- 删除时必须同步处理引用该节点的权限范围，不能留下悬空授权。

如果操作者只有父区域单点权限，新建子区域后可能立即失去对新节点的可见性。实际产品必须明确选择一种策略：自动补充新节点的管理范围，或接受创建后不可见。若采用自动补充，只能扩展 `AREA`，不能顺带扩展 `RES_AREA`。

### 9.2 组织

组织结构写入同时需要组织管理功能和相应 `ORG` 范围。

- 新增时检查父组织；
- 修改和删除时检查目标组织；
- 更换父组织时同时检查旧组织和新父组织；
- 不能移动到自身或自身后代；
- 移动后当前节点及全部后代的层级关系必须一致；
- 只能删除没有子组织、没有用户的叶子组织；
- 删除时不能留下悬空的 `ORG` 授权。

### 9.3 业务资源

资源挂在区域节点下，但后台管理与应用端使用不同权限域：

- 后台新增资源时检查目标区域的 `AREA`；
- 后台修改或删除资源时检查原区域的 `AREA`；
- 后台移动资源时同时检查原区域和目标区域的 `AREA`；
- 应用端查看或操作资源时使用 `RES_AREA`；
- 资源可见不代表拥有所有应用操作，仍需检查对应功能权限。

## 10. 一致性、并发与缓存

### 10.1 事务边界

以下变更必须原子完成：

- 角色主体及其权限变化；
- 用户主体及其角色绑定；
- 树节点层级变化及全部后代关系更新；
- 区域两个排序值的交换；
- 删除节点及其权限引用清理。

任何一步失败都必须回滚全部相关变化。

### 10.2 并发控制

实现必须防止：

- 两个管理员同时编辑导致后提交者静默覆盖前者；
- 两次树结构变化产生环或错误层级；
- 两次区域排序交换读取旧排序值后互相覆盖；
- 删除最后一个超级管理员；
- 操作者在敏感写入期间已经被收权却仍扩大授权。

具体可以使用行锁、版本号或其他并发控制方式，但不能牺牲上述业务不变量。

### 10.3 权限快照与缓存

缓存不是权限模型的必需组成，实际项目可以根据规模选择实现。

如果缓存用户权限结果，必须保证：

- 权限关系变更提交成功后，受影响用户不能继续长期使用旧权限；
- 事务失败不能发布未提交状态；
- 正在加载的旧权限不能在失效事件之后重新写回缓存；
- 缓存异常时应回源可信数据或拒绝，不能扩大权限；
- 缓存内容是不可变权限事实，不混入请求对象或业务临时状态。

## 11. 数据暴露与安全边界

- 所有权限判断必须在服务端完成；
- 元数据、详情、树节点、搜索、统计、下拉列表和导出同样需要授权；
- 越权时不应泄露对象名称、父节点、组织关系等可枚举信息；
- 客户端不能指定操作者、角色归属或数据权限域来影响鉴权；
- 权限不足与目标不存在的对外表现应符合实际项目的安全策略；
- 内部错误、查询细节、密钥和调用栈不能暴露给客户端。

## 12. 审计

角色授权、用户角色绑定、超级管理员变更、区域排序、组织移动等敏感操作应该记录追加式审计事件。

审计至少需要表达：

- 谁执行；
- 执行了什么操作；
- 操作了哪个对象；
- 变更前后状态；
- 成功或失败及原因；
- 请求追踪信息；
- 发生时间。

审计必须与业务提交结果一致，普通应用日志不能替代权限审计。

## 13. 另一个 Agent 的实现步骤

另一个 Agent 接到真实项目后，应按以下顺序工作：

1. 阅读实际项目的架构、认证方式、数据模型和已有编码规范。
2. 将本文中的用户、角色、功能权限、三个数据权限域映射到实际业务对象。
3. 列出“业务操作 → 功能权限 → 固定数据权限域 → 目标节点”的授权矩阵。
4. 确认实际项目中哪些规则已经存在，哪些需要补充，避免另建一套平行架构。
5. 先实现身份读取、默认拒绝、功能权限和数据范围判断。
6. 再实现列表过滤、角色二次授权、用户角色绑定和树结构写入规则。
7. 最后补充事务、并发、缓存失效、审计和验收测试。

Agent 不应假定本文中的任何接口名、类名、函数名、表名或目录真实存在。遇到实际项目与本文不一致时，应保留核心安全语义，并根据用户最新提示调整业务策略。

## 14. 验收场景

### 14.1 身份和默认拒绝

- 没有身份、无效用户、禁用用户均被拒绝；
- 普通用户没有角色时没有任何隐式权限；
- 超级管理员无需普通角色即可覆盖全部权限域。

### 14.2 功能与数据权限

- 只有功能权限、没有数据范围时不能访问对象；
- 只有数据范围、没有功能权限时不能执行业务操作；
- 多角色权限按并集生效；
- `AREA`、`ORG`、`RES_AREA` 不能互相替代；
- 单点授权不覆盖后代，子树授权覆盖当前和未来后代；
- 空数据范围不会返回全量数据；
- 导航祖先可展示但不可访问。

### 14.3 角色与二次授权

- 普通管理员不能管理他人角色；
- 不能授予自己没有的功能权限；
- 单点权限不能向下授予子树；
- 任一越权变化会使整次角色保存失败；
- 省略、显式清空和增量变化具有不同语义；
- 当前不可见的历史权限不会在保存时丢失；
- 创建人被收权后，已保存角色仍按自身权限生效。

### 14.4 用户管理

- 普通管理员只能看到和管理 `ORG` 范围内的普通用户；
- 用户不能被移动到操作者 `ORG` 范围外；
- 普通管理员只能主动分配自己创建的角色；
- 当前不可分配的历史角色不会在编辑时丢失；
- 普通管理员不能创建或管理超级管理员；
- 不能删除当前账号，系统始终保留超级管理员。

### 14.5 区域、组织和资源

- 区域更新不能改变父节点；
- 区域排序只允许同父节点的两个区域交换排序值；
- 区域排序不要求相邻，不修改其他节点、父节点或层级关系；
- 组织不能移动到自身后代，移动后整棵子树关系正确；
- 非叶子节点或仍挂载业务对象的节点不能删除；
- 后台资源管理使用 `AREA`，应用端资源访问使用 `RES_AREA`。

### 14.6 一致性

- 任一关联写入失败时整次业务变更回滚；
- 并发编辑、树移动和排序不会静默丢失更新；
- 权限被收回后不会因缓存回填再次获得旧权限；
- 敏感权限变化具有完整且可信的审计记录。

## 15. 不允许的实现方式

- 信任客户端提交的当前用户 ID；
- 只依赖前端隐藏菜单或按钮；
- 只检查功能权限或只检查数据权限；
- 混用三个数据权限域；
- 无数据范围时查询全量数据；
- 先加载全量数据再进行内存分页；
- 通过逐角色、逐节点、逐对象查询制造大量重复访问；
- 根据前端缺失字段推断用户要清空权限；
- 保存角色时删除操作者当前看不到的历史权限；
- 把普通管理员的单点权限放大成可转授的子树权限；
- 把角色创建人的当前权限作为已保存角色持续生效的前置条件；
- 允许客户端切换业务使用的数据权限域；
- 在事务提交前发布新的权限缓存状态。

## 16. 最终交付检查

另一个 Agent 宣布权限框架完成前，至少确认：

- [ ] 所有受保护业务都有明确的功能权限；
- [ ] 所有对象型业务都有服务端固定的数据权限域；
- [ ] 身份统一从可信请求上下文获取；
- [ ] 功能权限和数据权限始终同时校验；
- [ ] 三个数据权限域没有混用；
- [ ] 列表、搜索、统计和分页均在数据源层过滤；
- [ ] 普通管理员不能授出超出自身的权限；
- [ ] 不可见历史权限和不可分配历史角色不会误删；
- [ ] 区域、组织和资源写入满足各自的树权限规则；
- [ ] 权限写入具有完整事务和必要并发保护；
- [ ] 缓存不会延长已收回权限的有效期；
- [ ] 默认拒绝、越权、枚举、并发和超级管理员保护测试通过。
