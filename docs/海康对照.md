# 海康 iSecure Center 真实平台对照验证

> 目的:用真实海康平台校验本权限系统设计是否合理。
> 时间:2026-06-09。方法:CDP 驱动 headless Chrome 登录真实海康平台(账号 wbc),
> 抓取角色/权限相关接口报文 + UI 原文,逐项与本系统设计对照。
> 探针脚本与截图为一次性调研产物,验证后已清理;本文保留全部关键证据(接口报文 + UI 原话)。

---

## 一句话结论

**本系统核心设计与真实海康高度吻合**:两权限维度、单根树 + 子节点继承、可授范围过滤(GrantableSet)、
二次授权(受控委派,含 `created_by`)全部对得上。
**唯一系统性差异**:海康多一个「**显式角色范围**」委派维度 —— 正是 `CLAUDE.md` 预留的「模型 B」升级方向,
本系统的 `role.created_by` 地基已具备,可平滑补齐。设计无需返工。

平台确认:`/portal/front/theme` 返回 `systemSubtitle: "iSecure Center"`、`themeSchema: "redblack"` ——
即本系统所仿的海康红黑风平台(HikCentral / iSecure Center 系)。

## 二、海康比本系统多的能力(可借鉴 / 升级方向)

1. **显式「角色范围」委派维度** ⭐(最重要)
   角色范围页原文:「请配置当前角色可授权的角色范围。如果需要进行二次授权时,可选择的角色范围包含:
   **下方列表中勾选的角色** _和_ **用户自行创建的角色**。」
   即海康委派可管范围 = `(显式勾选的角色) ∪ (自己创建的角色)`。
   - 本系统只实现了后半(`created_by`,只能管自己创建的);前半「显式勾选」即 `CLAUDE.md` 预留的**模型 B**。
   - 补齐成本低:`role.created_by` 已可靠,只需加一张「角色 → 可管理角色」关系表 + 在委派校验里并入这层。

2. **资源范围「自动匹配模式」**(`autoMatchModeByDefault`):按规则自动纳入匹配资源,而非纯手工勾树。本系统目前仅手工勾选。

3. **每个数据维度独立「授权范围开关」**(`showAuthRangeSwitch / openAuthRange`):可单独控制某维度是否参与二次授权;本系统是全局一套合并逻辑。

4. **业务资源模块更多更细**:视频监控 / 门禁 / 停车场 / 电视墙 / 可视对讲 / 消防 / 事件联动 / 智能监控 各成一个数据维度,每类资源带独立 CRUD 操作集;本系统目前聚焦摄像头一类。

5. **区域树搜索框** ✅(本次已补齐,2026-06-10)
   真实海康(用户提供 PixPin 截图,2026-06-10)区域树搜索行为:
   - 结果**按局部树展示**——命中分支的祖先节点作为上下文一并显示,匹配节点的命中子串**高亮(海康红)**,而非平铺列表。
   - 区域过多时**最多返回前 500 条**,并给提示横幅:「**搜索结果过多,仅展示前 500 条,建议缩小搜索范围。**」
   - 本系统已对齐:`SearchAreas` 回传每条匹配的祖先链(`Ancestors`)+ 硬上限 `searchLimit=500`;前端 `renderSearchTree`/`hlMatch` 拼命中分支树并高亮,超 500 同款横幅;搜索同样叠加可见性 WHERE 下推(无权区域搜不到)。详见 `docs/测试报告.md` §十六 PG5/PG15/PG16/PG17。

6. **角色配置区域树 = 级联勾选 + 推断 nodeType** ✅(本次已对齐,2026-06-11)
   CDP 登录真实海康(`/isupm/role` 添加角色 → 安保区域管理权限)实测:
   - 区域树就是**普通 el-tree 级联勾选框**,**没有「包含子节点」开关**(只有「切换为自动匹配模式」链接=另一种模式);按层惰性加载(节点带展开箭头,点开才查下一层)。
   - **勾选语义**(抓 `POST /isupm/ui/role/updateRoleTree` 报文为据):每条授权是 `{indexCode, nodeType}`:
     - 勾某节点(**未展开**)→ 保存为 `{node, nodeType:"subTree"}` 一条,代表整棵子树(= 本系统 `includeChild:true`)。
     - 勾后展开、**取消某个子节点** → 父降为 `{node, nodeType:"singleNode"}` + 其余被勾子各自成条(= `includeChild:false` + 递归)。
     - 另有 `updateRoleResourceTypeAuth` 带 `allContainSub:true`(默认含子)/`autoMatchMode:false`。
   - 即海康 = **级联勾选 + 从「整棵子树是否全勾」推断 subTree/singleNode**,而非显式开关。
   - 本系统已对齐:去掉早先的「含子节点」开关,改为级联勾选框(`roleTree` 的 `chk`/`sub` 状态 + `rtScopes` 推断导出);勾未展开节点=子树,展开后可单独取消子→父半选(`singleNode`);保存全勾→`includeChild:true`、半选→`includeChild:false`。整层一次加载不分页(`/api/role-area-children`),保证「取消某子时同层兄弟全在手」使推断精确。详见 `internal/service/paging.go` `RoleAreaChildren` 与 `resource/public/index.html` 角色配置区域树一节。

## 三、关键证据留档

### 3.1 平台与菜单双域
- `/portal/front/theme` → `systemName:"安防管理平台"`, `systemSubtitle:"iSecure Center"`, `themeSchema:"redblack"`。
- `/portal/front/common/basicInfo` → `showSystemConfigPage:true`(wbc 可进系统配置)、`skin:"redblack"`。
- 应用域菜单:`/portal/front/menu/getHomeMenu?type=app` → 首页/综合管控/视频监控(实时预览·录像回放·图片查询)/一卡通/车辆管控/网络管理。
- 系统域菜单:`/portal/front/menu/getConfigMenu` 顶层含:人员信息管理(`iSecure Center_config01`)、车辆信息管理、
  **安保区域管理(`rtree_region` → /region)**、设备管理、各业务配置、高级参数配置、界面配置。
- 角色/用户管理路由(`isupm` 微前端,挂在「人员信息管理」下):
  - 角色管理 `isupm_role` → `/isupm/role`
  - 用户管理 `isupm_user` → `/isupm/user`
  - 人员账户管理 `isupm_account` → `/isupm/account`
- `userinfo` 面包屑确认顶层域名为「系统管理」:`{role:["系统管理","人员信息管理","角色管理"]}`。

### 3.2 角色权限的维度结构 —— `GET /isupm/ui/roleUi/moduleViews?roleId=`
```
menu_config  系统管理菜单权限   configType=sys_mgr_config     (功能·SYS域)
menu_app     应用菜单权限       configType=app_menu_config    (功能·APP域)
rtree        安保区域管理权限   configType=sys_mgr_config     (数据·区域树/AREA)
isfd         组织管理权限       configType=sys_mgr_config     (数据·组织树/ORG)
role         角色范围           configType=sys_mgr_config     (委派维度)
vms/acs/pms/tvmc/scpms/vis/fpms/els/frs ... configType=business_res_config (数据·业务资源)
```
对应本系统:功能权限(menu_config + menu_app)+ 数据权限(rtree 区域 / isfd 组织 / 业务资源)+ 委派(role 角色范围)。

### 3.3 默认「包含子节点」—— `GET /isupm/ui/roleUi/roleRelatedConfigInfo`
```json
{"autoMatchModeByDefault":false,"allContainSubByDefault":true}
```
对应本系统 `include_child` 默认继承子树。

### 3.4 功能权限树带可授标志 —— `GET /isupm/ui/role/menus?menuType=menu_config|menu_app`
节点结构:`{name, indexCode, parentIndexCode, canCheck, checked, leaf, open}`。
`canCheck` = 该节点是否可被勾选/授予 = 本系统 GrantableSet 可授范围过滤。

### 3.5 区域数据权限 —— `roleUi/tabViews?moduleCode=rtree` 与 `role/regions`
```json
// tabViews(rtree)
{"tabCode":"rtreeTab","tabName":"区域下资源","treeType":"region",
 "refResTypes":[{"resType":{"resTypeName":"安保区域"},
                 "resOperList":[{"resOpName":"查看","resOpCode":"region1","value":1}]}],
 "showAuthRangeSwitch":true,"openAuthRange":false,
 "showContainSub":true,"containSub":true}
// role/regions 根:单根
{"name":"保伦电子","indexCode":"root000000","parentIndexCode":"0","canCheck":true,"leaf":false}
// 子节点按 parentIndexCode=root000000 懒加载:1栋/2栋/3栋/4栋宿舍/外围监控/波峰焊+老化/测试区域/测试事件
```
对应本系统:单根区域树 + 物化路径懒加载 + 节点 `canCheck` 可授过滤 + 资源类型/操作 两层模型。

### 3.6 角色列表带委派标志 —— `POST /isupm/ui/role/findPageRoles`
请求 `{"pageSize":20,"pageNo":1,"order":"desc","roleName":""}`;返回每行:
```

createTime, updateTime, canEdit:false, canDelete:false
```
wbc 对所有他人创建的角色 `canEdit=canDelete=false`(列表页删除按钮置灰)。
对应本系统:角色列表展示「创建用户」列 + 按 `created_by`/超管 控制可改可删。

### 3.7 二次授权 UI 原文(新建角色页 `添加角色`)
- 「权限配置」副标题:**「如果当前角色需要进行二次授权时,当前角色权限配置的内容将作为该角色二次授权的权限范围。」**
- 系统管理菜单权限页:**「请配置当前角色在系统管理中的菜单访问权限。如果需要进行二次授权时,需要勾选"角色管理"或"用户管理"的菜单权限,可选择的权限范围为此处配置的系统管理菜单权限。」**

## 四、建议

- 设计**正确性已被真实海康全面验证**,核心模型(两维度 / 单根树继承 / 可授范围 / 二次授权 + created_by)不必返工。
- 若继续迭代,**优先补「显式角色范围」(模型 B)**:这是与海康唯一的结构性差距,地基(`created_by` 可靠)已就绪。
- 次优可考虑:数据维度的「授权范围开关」颗粒度、资源「自动匹配模式」。
